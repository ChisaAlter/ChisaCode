## 迁移原则

### ✅ DO

1. **渐进式迁移** - 小步快跑，每次改动可验证
2. **向后兼容** - 旧代码和新代码可以共存
3. **测试优先** - 先有测试覆盖再重构
4. **团队共识** - 每个阶段都要团队 Review
5. **文档同步** - 更新文档和示例

### ❌ DON'T

1. **大爆炸式重构** - 不要一次性重构整个模块
2. **删除旧代码** - 保留旧代码直到新代码稳定
3. **强制迁移** - 不要强制所有人立即使用新模式
4. **破坏 API** - 不要破坏现有公共 API
5. **忽略测试** - 不要在没有测试的情况下重构

## 第 1 阶段: 新代码使用新模式

**时间**: 第 1-2 周  
**目标**: 所有新代码使用新模式，不影响现有代码  
**风险**: 🟢 低

### 行动项

#### 1.1 更新团队规范

在 `CONTRIBUTING.md` 中添加：

```markdown
## 新代码规范

### 必须使用

1. **DI Container** - 所有新服务必须使用依赖注入
2. **TestableQueue** - 所有新的异步测试必须使用
3. **类型化错误** - 所有新错误必须使用 `@server/core/errors`

### 示例

参考 `docs/integration-examples.md` 获取完整示例。
```

#### 1.2 创建模板

参考 `docs/integration-examples.md` 中的完整服务示例。

#### 1.3 团队培训

- 举办 1 小时的培训会议
- 演示新模式的使用
- 分享 `docs/integration-examples.md`

## 风险管理

### 常见风险与缓解措施

#### 风险 1: 破坏现有功能

**缓解**:
- 每次改动都有完整测试覆盖
- 小步快跑，逐个模块迁移
- Code Review 严格把关

#### 风险 2: 团队不接受新模式

**缓解**:
- 提供完整文档和示例
- 举办培训会议
- 选择简单模块试点

#### 风险 3: 性能回退

**缓解**:
- 每次重构都要性能测试
- 对比重构前后性能
- 如果下降 > 10%，重新评估

### 回滚计划

每个阶段都可独立回滚：

```bash
# 回滚单个 commit
git revert <commit-hash>

# 回滚单个文件
git checkout <commit-before-refactor> -- src/path/to/file.ts
```

## 总结

### 关键成功因素

1. **团队共识** - 所有人理解并支持迁移
2. **小步快跑** - 每次改动可验证，可回滚
3. **测试先行** - 先有测试再重构
4. **文档齐全** - 示例、模板、指南一应俱全
5. **渐进式** - 新旧代码可以共存
